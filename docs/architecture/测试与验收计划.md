# 测试与验收计划

## 1. 测试层次

| 层次 | 覆盖内容 | 工具建议 |
| --- | --- | --- |
| 单元测试 | 价格计算、账本、状态机、权限、支付验签适配层 | pytest |
| 集成测试 | MySQL、MinIO、Redis | Docker Compose / Testcontainers |
| API 契约测试 | OpenAPI 与 FastAPI 路由、响应、错误码一致 | Schemathesis 或自建 pytest |
| 端到端测试 | 浏览器完整用户路径 | Playwright |
| 故障测试 | 重复提交、重复回调、API 重启、Provider 超时 | pytest + 容器控制 |

## 2. MVP 验收场景

### A. 邮箱与多端会话

1. 用户使用邮箱注册，收到验证码并验证成功。
2. 未验证用户不能登录或创建任务。
3. 登录返回短期 access token 和 Cookie 内 refresh token。
4. 第 6 台设备登录时，第 1 台设备被撤销；最大设备数可由配置调整。
5. 单设备退出不影响其他 Session；全部退出后所有 refresh token 失效。

### B. 资产上传

1. 已登录用户申请预签名 URL 并直接上传 MinIO。
2. 服务端确认上传后创建资产元数据。
3. 另一用户无法获得该资产下载 URL。
4. 超出类型、大小或时长限制的文件被拒绝。

### C. AI 任务与积分

1. 用户余额充足，创建转写任务返回 `202 + job_id`。
2. 同一个 `Idempotency-Key` 重复提交只创建一个 Job 和一笔预扣。
3. 任务成功后 Job 为 `SUCCESS`，结果可访问，积分正确结算。
4. 任务失败且无结果时 Job 为 `FAILED`，积分全额退款。
5. 用户在 `PENDING` 取消时 Job 为 `CANCELED`，默认不退款。
6. 用户在 `RUNNING` 时取消请求被拒绝。

### D. 支付

1. 创建积分商品订单时使用 `Idempotency-Key`。
2. 支付成功 Webhook 验签、金额、商户订单号均正确时，订单变为 `PAID` 并发放积分。
3. 相同 Provider 交易号的重复回调不会重复发放积分。
4. 金额不一致、签名错误的回调被拒绝并记录审计事件。
5. 浏览器跳转成功、但未收到有效 Webhook 时，订单仍不是 `PAID`。

## 3. 发布门槛

- 关键单元测试、集成测试、端到端 MVP 用例全部通过。
- OpenAPI 契约测试通过。
- 无高危依赖漏洞或明文密钥泄漏。
- 重复任务、重复支付回调、供应商超时三类故障已演练。
- 数据库与对象存储恢复演练通过。
