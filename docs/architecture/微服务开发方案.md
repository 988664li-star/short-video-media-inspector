# 微服务开发方案

## 1. 目标与范围

本方案面向当前“抖音媒体检查台 / 视频分析”项目的演进：现有 React + FastAPI 后端逐步具备多用户、任务异步执行、文件对象存储、积分支付与通知能力。

目标不是立即拆成大量独立服务，而是先建立清晰的服务边界和基础设施；当并发、团队规模或业务复杂度增长时，可以平滑拆分。

当前项目中已经具备内容解析、媒体代理、转写、分镜、AI 生成工作台等能力。用户体系、积分支付、对象存储和通知体系属于新增能力。

### 已确认的第一阶段边界

- 仅使用邮箱注册、验证和登录，不接入手机号或短信。
- 默认允许 5 台设备同时登录，作为可配置项；达到上限时踢出最早活跃设备。
- 商业模型以积分为核心；积分包和能力价格均由后台配置。订阅商品保留扩展能力，但不要求第一版启用。
- 用户主动取消任务默认不退款；系统或模型供应商失败且没有可用结果时自动退款。
- 第一批支付 Provider 为微信支付和支付宝；团队/企业账号第一阶段不做。

## 2. 目标架构图

当前阶段采用模块化单体：前端通过 FastAPI 调用业务模块，业务模块直接使用 MySQL、Redis 和 MinIO，并按需调用外部 AI 与支付服务。

## 3. 架构原则

1. **每个服务只负责一个业务领域**：用户、项目分析、AI 任务、支付积分和通知分别负责自己的业务。
2. **每个模块只拥有自己的数据边界**：模块间通过清晰的服务接口协作，不直接耦合存储细节。
3. **即时操作走同步 API**：登录、查询项目、创建订单等需要立即响应的操作使用 HTTP API。
4. **耗时操作由 API 或外部能力服务处理**：转写、分镜和视频生成统一记录任务状态；外部服务异步时由 API 查询其状态。
5. **数据库保存事实，文件存对象存储**：MySQL 是业务状态来源，MinIO 保存媒体资产；进程内状态不作为最终依据。
6. **先模块化，后拆服务**：第一阶段可在一个 FastAPI 仓库内按领域模块开发；接口与数据边界保持独立，后续再部署为独立服务。

## 4. 服务划分

| 服务 / 组件 | 核心职责 | 对外接口 | 数据边界 |
| --- | --- | --- | --- |
| API Gateway | HTTPS 入口、路由、鉴权前置、限流、审计 | 将 Web 请求路由至后端模块 | 无业务库 |
| 用户与权限模块 | 邮箱注册登录、JWT、角色、会话、能力规则与通知偏好 | 登录、刷新 Token、读取当前用户、校验能力规则 | `user_db` |
| 内容与项目模块 | 抖音解析、项目、媒体元数据、创建分析任务 | 创建项目、提交分析、查询项目/结果 | `project_db` |
| AI 任务模块 | 转写、分镜、替换方案、视频生成与任务状态管理 | 查询任务状态、取消任务（可选） | `task_db` |
| 支付与积分模块 | 积分商品、订单、支付下单、支付回调、退款、积分账本；订阅为可选扩展 | 创建订单、查询订单/积分 | `billing_db` |
| 通知模块 | 站内信、邮件、短信、任务完成通知 | 查询通知列表、标记已读 | `notification_db`（后续） |

## 5. 基础设施选型

| 基础设施 | 选型 | 作用 | 首次启用时间 |
| --- | --- | --- | --- |
| 关系型数据库 | MySQL（InnoDB） | 用户、项目、任务、订单、积分账本与可选订阅等事务数据 | 第一阶段 |
| 对象存储 | MinIO | 视频、音频、关键帧、封面、分镜、AI 生成结果 | 第一阶段 |
| 缓存 | Redis | 会话、JWT 黑名单、权限缓存、限流计数、短期任务查询缓存 | 第一阶段 |
| 反向代理 | Nginx | TLS、前端静态资源、反向代理、基础限流 | 第一阶段 |
| 监控 | OpenTelemetry + Prometheus + Grafana + Loki | Trace、指标、日志、告警 | 第二阶段 |
| 容器编排 | Docker Compose；后续 Kubernetes | 本地/单机部署；规模化部署 | Compose 第一阶段，K8s 后续 |

### 5.1 MySQL

初期可以使用 **一个 MySQL 实例**，但创建独立数据库和独立账号，避免服务之间直接跨库操作：

```text
user_db          用户、角色、权益、通知偏好
project_db       项目、解析记录、媒体元数据
task_db          AI 任务、执行状态、结果索引
billing_db       商品、订单、支付记录、退款、积分账本、可选订阅
```

后期单个服务压力显著增长时，再将其迁移为独立 MySQL 实例。所有核心表使用 InnoDB，任务、订单、支付回调必须有唯一业务键与事务控制。

### 5.2 MinIO

MinIO 使用 S3 兼容 API，适合自建部署并可在未来迁移到云对象存储。服务端只保存对象键和元数据，不把视频、图片或音频二进制内容写入 MySQL。

建议 Bucket：

```text
raw-media/          原始视频、音频、封面
analysis-assets/    下载源文件、关键帧、镜头素材、转写附件
generated-media/    AI 生成视频、图片与导出文件
temporary-upload/   未完成处理的临时上传文件
```

规则：

- Bucket 默认私有；客户端通过后端签发的 **预签名 URL** 直接上传和下载。
- 对象键包含环境、用户和项目，例如 `prod/user/{user_id}/project/{project_id}/...`。
- 设置生命周期策略：临时文件自动删除；分析源文件按业务保留周期清理。
- MySQL 中保存 `bucket`、`object_key`、`content_type`、`size`、`checksum`、`owner_id` 和创建时间。

文件上传链路：

```text
Web → 内容服务：申请预签名上传 URL
Web → MinIO：直接上传文件
Web → 内容服务：确认上传完成
内容服务 → MySQL：保存文件元数据
AI 任务模块 → MinIO：下载处理；将结果写回 MinIO
```

### 5.3 Redis

Redis 不是业务最终数据源，只用于可丢失、可重建的数据：

```text
session:{user_id}                 登录会话或刷新 Token 状态
jwt:blacklist:{jti}               已注销 Token
entitlement:{user_id}             用户权益缓存
ratelimit:{route}:{subject}       限流计数
task:status:{task_id}             短期任务状态缓存
```

必须设置 TTL 和内存上限；订单、支付状态、任务最终结果仍写入 MySQL。

## 6. 核心交互流程

### 6.1 登录与鉴权

```text
Web → API Gateway → 用户与权限服务
用户与权限服务 → user_db：验证账号和密码
用户与权限服务 → Web：访问 JWT + 刷新 Token
Web → API Gateway：携带 Bearer Token
API Gateway / 服务：校验 Token、角色和能力规则
```

### 6.2 内容分析与 AI 任务

```text
Web → 内容与项目服务：提交抖音链接或媒体
内容与项目服务 → project_db：创建项目与分析任务（PENDING）
AI 任务模块 → MinIO：下载媒体、写入关键帧和结果文件
AI 任务模块 → AI 模型服务：转写、分镜、生成
AI 任务模块 → task_db：更新 SUCCESS / FAILED 和结果索引
通知模块：根据任务状态创建站内通知或发送邮件
```

### 6.3 支付、积分与可选订阅

```text
Web → 支付与积分服务：创建积分商品订单
支付与积分服务 → billing_db：创建 PENDING 订单
支付与积分服务 → 支付渠道：发起支付（微信支付 / 支付宝）
支付渠道 → 支付与积分服务：Webhook 回调
支付与积分服务 → billing_db：校验并原子更新订单为 PAID，并写入 CREDIT_GRANT 账本
支付与积分模块：刷新可用权益缓存，并创建支付成功通知
```

支付回调必须校验签名、支付金额、商户订单号和当前订单状态；同一回调重复到达时必须幂等。

## 7. 部署建议

### 阶段一：模块化单体 + 基础设施

适合当前项目和小团队。

```text
Nginx
├── frontend（React 静态资源）
└── backend-api（FastAPI，按业务模块组织）

MySQL + MinIO + Redis
```

优先完成：把现有 `backend/data/` 的可持久媒体资产逐步迁移至 MinIO；把需要长期保存的 SQLite 数据迁移至 MySQL。

### 阶段二：按需拆分服务

当用户、支付或 AI 任务需要独立扩容时，将领域模块拆为独立进程/镜像：

```text
gateway
user-service
content-service
payment-service
notification-service
```

初期使用 Docker Compose；多机、高可用或需要弹性扩缩容时再评估 Kubernetes。不要因“微服务”而过早引入 Kubernetes。

## 8. 开发顺序

1. 引入 Docker Compose：MySQL、MinIO、Redis、Nginx。
2. 定义项目、媒体资产、分析任务的数据模型，并将长期存储从本地目录/SQLite 迁移到 MySQL + MinIO。
3. 实现用户与权限模块：邮箱验证、用户、JWT、可配置多端会话、角色与能力规则。
4. 实现任务状态、失败重试和对象生命周期清理。
5. 实现支付与积分：积分商品、订单、回调验签、CREDIT_GRANT 账本；接入微信/支付宝前先完成模拟环境测试。订阅仅在需要时启用。
6. 实现通知模块与管理后台。
7. 接入 OpenTelemetry、Prometheus、Grafana 和集中日志。
8. 根据运行数据决定是否拆出独立服务与 Kubernetes。

## 9. 不建议现在引入的组件

- **Elasticsearch / OpenSearch**：除非项目、文稿或素材需要复杂全文检索；常规查询先用 MySQL 索引。
- **Kubernetes**：单机或少量服务器阶段，Docker Compose 维护成本更低。
- **跨服务共享数据库**：短期方便，长期会让服务无法独立演进。
